# СибКодБокс vNext

Комплект для обновления существующего игрового автомата и панели учителя. Статическая часть не содержит GitHub Personal Access Token, Supabase service-role key или паролей. В `app-config.js` находится только публичный Supabase URL и anon key (это браузерный ключ, его безопасность обеспечивается RLS и Edge Functions).

## 1. Состав проекта

```text
index.html                         игровой автомат
teacher.html                      панель учителя / разработчика
app-config.js                     публичные параметры клиента
assets/kiosk.css                  стили автомата
assets/teacher.css                стили панели
js/audio.js                        перенесённая звуковая система старого автомата
js/shared.js                       общие функции и IndexedDB
js/kiosk.js                        карусель, QR, таймер, рекорды, Arduino, настройки
js/teacher.js                      Supabase Auth, QR, ZIP, модерация
sw.js                              shell cache + офлайн-файлы игр из IndexedDB
games/snake/                       тестовая «Змейка»
games/reaction/                    тестовая «Реакция»
games/guess-number/                тестовая «Угадай число»

supabase/migrations/001_v9_to_vnext.sql

supabase/config.toml               JWT-настройки функций
```

## 2. Что изменено в архитектуре

- **Каталог игр:** новая версия читает `games`, а не `config.games_json`. `files_json` хранит список всех файлов игры: `path`, `raw_url`, `mime`, `size`. В `games/<slug>/` публикуются `index.html`, `icon.png` и остальные ассеты. На период миграции SQL-триггер пересобирает совместимый `config.games_json` из `games`; дополнительные поля старых карточек сохраняются в `games.legacy_json`, поэтому старые киоски продолжают получать прежний формат каталога.
- **QR и сессии:** QR содержит случайный одноразовый 256-битный токен и время истечения QR. В БД хранится только SHA-256 токена. QR можно активировать в течение 30 минут после выдачи; после сканирования сервер запускает выбранную длительность сессии и возвращает `expires_at`. Сам QR повторно использовать нельзя.
- **Таймер:** автомат вычисляет остаток как `expires_at - Date.now()`. Потеря интернета не останавливает и не продлевает текущую сессию. Новые QR без сети не принимаются, рекорд без сети не ставится в очередь и не считается сохранённым.
- **Офлайн:** Service Worker кэширует оболочку автомата и CDN-библиотеки; синхронизатор получает все перечисленные в `files_json` файлы игр в IndexedDB. При запуске `kiosk.js` собирает HTML-документ из IndexedDB и встраивает найденные локальные ресурсы как data URL в `iframe` с opaque origin. Это не открывает игре IndexedDB или DOM автомата и поддерживает типовые относительные пути HTML/CSS/классических JS-скриптов. Сам Service Worker не управляет содержимым sandboxed iframe.
- **Права:** `teacher` может выпускать QR, загружать игры и модерировать ники. `developer` имеет те же права плюс редактирование/архивацию игр и принудительную синхронизацию. Роль проверяется на сервере через Auth JWT и `admins`.
- **GitHub:** токен существует только в Supabase Function Secrets. ZIP передаётся Edge Function; браузер не знает GitHub-токен.
- **Совместимость:** звуковая система старого автомата вынесена в `js/audio.js`; перенесены рекорды, техработы, локальные настройки, экспорт настроек, Web Serial/Arduino и клавиатурное управление. Старые `tickets`, `records`, `incidents`, `config` и их данные сохраняются.

## 3. Переход с v9

Делайте резервную копию Supabase и репозитория до миграции.

1. Откройте Supabase → SQL Editor и выполните `scbb.txt` целиком. Скрипт создаёт новые таблицы и функции, добавляет поля в `records`, индексирует данные, включает новые RLS-политики и оставляет legacy-таблицы на месте.
2. В том же SQL Editor выполните `supabase/migrations/001_v9_to_vnext.sql`. Он копирует массив `config.games_json` в `games`, переносит `player_name` в `nick`, создаёт архивные карточки для game_id из старых записей, чтобы сохранить их ссылки, и оставляет `games_json` для переходного периода.
3. Проверьте `games`, `sessions`, `admins`, `records`, `tickets`, `incidents`, `config`. Старые записи в `tickets` и `records` не удаляются. Старые `records.player_name` остаётся; новое приложение синхронно пишет `nick` и `player_name`.
4. После успешного переноса не удаляйте `config.games_json`, пока на площадке работают старые автоматы. Удаление — только отдельным поздним шагом после инвентаризации всех киосков.
5. При изменении `games` SQL-триггер обновляет зеркальный `config.games_json` для старых автоматов. Старые карточки сохраняют дополнительные ключи в `games.legacy_json`; новые карточки получают совместимые поля `id/title/description/genre/author/url/iconUrl`. Не отключайте триггер и не удаляйте `games_json`, пока работают старые автоматы.
6. В старом `config` удаляются известные ключи с токенами (`github_token`, `github_pat`, `gh_token`, `teacher_token`, `service_role_key`). Старые RLS policies, опиравшиеся на скомпрометированный статический teacher-token, удаляются. Legacy `tickets` и исторические `records` сохраняются; анонимный автомат может только читать tickets и перевести `used` из false в true.

**Важное ограничение перехода:** старые QR-билеты из `tickets` остаются в базе, старые автоматы могут их прочитать и пометить использованными. Старый `teacher.html` с PIN/статическим токеном после новой RLS-схемы не сможет выпускать билеты или менять административные данные. Для новых QR используйте новый `teacher.html` и Auth. Это намеренный отказ от небезопасной старой авторизации.

## 4. Подготовка Supabase Auth

1. В Supabase → Authentication → Users создайте пользователей учителей и разработчиков. Отключите публичную регистрацию пользователей, если она не требуется.
2. Для каждого пользователя скопируйте UUID из `auth.users` и назначьте роль SQL-командой:

```sql
insert into public.admins(id, role)
values ('UUID_ИЗ_AUTH_USERS', 'teacher');
-- Для разработчика используйте role = 'developer'.
```

3. Никогда не назначайте роль из браузера. Запись `admins` создаётся владельцем проекта через SQL Editor.

## 5. GitHub и Supabase Edge Functions

Репозиторий: `NasDail/SibCodeBox`, ветка `main`, каталог публикации `games/`. Уже существующую папку `Games/` с заглавной буквы не удалять: новые игры будут публиковаться в отдельную `games/`.

На компьютере с Supabase CLI:

```powershell
supabase login
supabase link --project-ref otsuvtcxnbdxrodayeta
```

Добавьте GitHub token (fine-grained PAT с `Contents: Read and write` только для `NasDail/SibCodeBox`) в Secrets Supabase. В PowerShell команда выглядит так; сам токен вводится только в терминал, не в чат и не в HTML:

```powershell
supabase secrets set GITHUB_TOKEN=ВСТАВЬ_ТОКЕН_ЛОКАЛЬНО GITHUB_OWNER=NasDail GITHUB_REPO=SibCodeBox GITHUB_BRANCH=main GAMES_ROOT=games
```

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Edge Functions обычно получают как штатные системные переменные Supabase. Если в конкретной среде они не установлены автоматически, добавьте URL и service-role key через `supabase secrets set` локально. Service-role key никогда не помещайте в `app-config.js`.

Разверните функции:

```powershell
supabase functions deploy admin-api
supabase functions deploy kiosk-api
supabase functions deploy publish-game
```

`supabase/config.toml` включает JWT-проверку gateway. `admin-api` дополнительно проверяет пользователя через Supabase Auth и роль `admins`. `kiosk-api` вызывается публичным автоматом с anon JWT, но каждая операция защищена одноразовым QR-токеном или session key. `publish-game` повторно проверяет Auth и роль перед доступом к GitHub.

## 6. Публикация статики

Скопируйте содержимое каталога `SibCodeBox_vNext` в корень репозитория `NasDail/SibCodeBox` и закоммитьте изменения. Не заменяйте старую папку `Games/` автоматически. Убедитесь, что в репозитории присутствуют `games/snake`, `games/reaction`, `games/guess-number`, `assets/`, `js/`, `app-config.js`, `sw.js`, `index.html`, `teacher.html` и `supabase/`.

Автомат открывайте по HTTPS (GitHub Pages/другой HTTPS-хостинг) или на `localhost`. Камера и Service Worker не работают на обычном HTTP в локальной сети. После первой загрузки в онлайне дождитесь статуса «ОФЛАЙН-КЭШ: ГОТОВ» и синхронизации каталога.

## 7. ZIP-правила

Архив должен включать `index.html` и `icon.png` в корне. Допускается одна общая папка-обёртка вокруг файлов: импортёр распознаёт её и поднимает содержимое на уровень игры. Вложенные каталоги, CSS, JS, изображения, аудио и прочие ассеты сохраняют относительные пути. Служебные `.log`, `.DS_Store`, `Thumbs.db`, `__MACOSX` пропускаются. Ограничение текущей версии: до 80 файлов и до 4 МиБ распакованных данных на игру. Пример `AutorallyM_game.zip` проходит проверку структуры после удаления обёртки `AutorallyM_game/`; большие `.log` из примера игнорируются.

## 8. Клавиши автомата

- `←` / `→` — перемещение по карусели (при активной сессии).
- `Enter` — запуск выбранной игры.
- `Esc` — назад / выйти из игры; игры передают `SCBB_GAME_ESCAPE` через `postMessage`.
- `F` — полный экран.
- `M` — звук.
- `F2` — настройки.
- `R` — таблица рекордов.

Тестовые игры отправляют результат в оболочку сообщением `postMessage({ type: 'SCORE', score }, '*')`.

## 9. Безопасность и ограничения

- Это комплект исходников и SQL для развёртывания, а не уже подключённый или проверенный в твоём Supabase проект. После настройки Auth, ролей, Secrets и деплоя Edge Functions нужно выполнить тестовый проход с реальными QR и GitHub публикацией.
- Anon key в браузере публичный по назначению. Безопасность зависит от RLS и серверных проверок; service-role/GitHub tokens публичными быть не должны.
- Старый формат каталога может содержать только `url` и иконку. Миграция перенесёт метаданные, но не сможет угадать полный список ассетов, если в старом JSON не было `files_json`. Для гарантированного запуска такой игры офлайн её нужно повторно загрузить из полного ZIP через новую панель.
- Игры запускаются в sandboxed iframe без `allow-same-origin` для изоляции от автомата. Локальные HTML/CSS/классические JS-ресурсы встраиваются в `srcdoc`; базовый loader переопределяет `fetch`, `setAttribute`, стандартные URL-свойства и CSS `url(...)`. Не гарантирована поддержка ES-модулей с import-графами, Web Worker/SharedWorker, Service Worker внутри игры, XHR, WebSocket, динамических URL, WASM через нестандартную загрузку и сторонних сетевых ресурсов в офлайн-режиме. Игры, требующие same-origin storage или доступа к родительской странице, нужно адаптировать.
- Публикация делает отдельный GitHub Contents API commit для каждого файла. При ошибке посередине возможны уже опубликованные файлы без записи в `games`; временные частичные файлы придётся проверить вручную.
- Кiosk проверяет отозванную онлайн-сессию примерно раз в 20 секунд; при потере сети не может узнать об удалённом отзыве и продолжает локальный таймер до ранее полученного `expires_at`. После восстановления связи серверная проверка снова выполняется.
- Ник проверяется в клиенте для удобства и обязательно повторно сервером/SQL trigger. Старый legacy insert path оставлен только для рекордов без `session_id` на переходный период; после обновления всех установленных автоматов его следует удалить отдельной миграцией.
- Потеря сети во время активной сессии: игра продолжает запускаться из IndexedDB, таймер идёт по серверному `expires_at`, новые QR не принимаются, рекорд без сети не отправляется и не буферизуется. После восстановления сети новый QR можно сканировать только после завершения предыдущей сессии.
